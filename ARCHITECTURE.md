# Architecture: The Lenny Growth Assistant

## 1. System overview

```
Vue 3 + TS frontend  <--REST/SSE-->  FastAPI backend  <--JSON-RPC/stdio-->  Pi subprocess (Node)
                                          |                                        |
                                          v                                        v
                                 Supabase Postgres                    Anthropic / OpenAI / Ollama
                                  (+ pgvector)
```

FastAPI owns all business logic and data access. The Pi subprocess owns
only the agent reasoning loop (deciding which tool to call and when) and
the LLM provider connection. Tool *execution* happens in Python — Pi never
touches the database directly.

## 2. Database schema (Supabase / Postgres + pgvector)

```sql
episodes(id, guest, title, youtube_url, video_id, publish_date,
         description, duration_seconds, view_count, topics text[])

chunks(id, episode_id -> episodes, content, chunk_index,
       embedding vector(384))    -- ivfflat index, cosine ops
                                 -- 384 dims: sentence-transformers
                                 -- all-MiniLM-L6-v2 (see note below)

sessions(id, title, llm_provider, llm_model, created_at, updated_at)

messages(id, session_id -> sessions, role, content, skill_used,
         retrieved_chunk_ids uuid[], created_at)

artifacts(id, message_id -> messages, session_id -> sessions,
          type, title, content, version, created_at)
```

Design notes:
- `episodes.topics` is seeded from the transcript repo's own pre-built
  `index/*.md` topic files at ingestion time, rather than re-deriving tags
  with an extra LLM pass.
- `messages.retrieved_chunk_ids` is stored for traceability — lets the UI
  (or an evaluator) verify which transcript passages backed a given answer.
- `artifacts.version` supports future "regenerate" flows without losing
  history; v1 always writes version 1.

### Embedding model (independent of the chat LLM toggle)

Embeddings are generated by a single local model —
**sentence-transformers `all-MiniLM-L6-v2`** (384 dims) — used for *both*
ingestion and query-time embedding, regardless of whether the active chat
LLM is OpenAI (cloud) or Ollama (local). This is a deliberate decoupling:
the embedding model's only job is turning text into a comparable vector
for pgvector search; it has no relationship to whichever model is writing
the final answer.

Reasoning:
- **Local demo stays fully local.** If retrieval depended on an OpenAI
  embedding call, the "local/offline" demo mode would still silently hit
  the network on every search. Using MiniLM for everything means the
  Ollama path has zero cloud dependency.
- **Vector-space consistency.** All chunks are embedded once, at
  ingestion time, into one space. If the embedding model ever differed
  between ingestion and query time (e.g. switched per LLM provider),
  cosine similarity would compare incompatible vectors and silently
  degrade retrieval quality with no obvious error.
- **One fewer external dependency and cost.** No OpenAI embeddings API
  usage at all; MiniLM runs locally at negligible cost/latency for this
  corpus size.

Tradeoff accepted: MiniLM's 384-dim embeddings are lower-fidelity than
OpenAI's `text-embedding-3-small` (1536 dims) on fine-grained semantic
similarity. This is acceptable here because the hybrid router already
narrows candidates by topic tag before vector search runs, reducing how
much weight falls on embedding precision alone.

## 3. API endpoints (FastAPI)

| Method | Path | Purpose |
|---|---|---|
| POST | `/sessions` | Create a new chat session |
| GET | `/sessions` | List sessions (sidebar) |
| GET | `/sessions/{id}` | Get session + message history |
| PATCH | `/sessions/{id}/config` | Update `llm_provider` / `llm_model` |
| POST | `/sessions/{id}/messages` | Send a message; SSE stream of response |
| GET | `/artifacts/{id}` | Fetch a specific artifact |
| GET | `/health` | Checks DB connectivity, Ollama reachability, Pi subprocess status |

SSE event types on `/sessions/{id}/messages`:
- `message_delta` — streamed response tokens
- `artifact_created` — `{id, type, title, content}`, fired once a
  `create_artifact` tool call completes
- `error` — structured error (missing key, provider unreachable, etc.)

## 4. Agentic routing logic

Three tools are registered with the Pi agent; Pi's model decides which
(if any) to call per turn based on the system prompt and user intent.
Default Pi file/bash tools are explicitly disabled — this agent answers
questions and emits content, it does not edit a codebase.

```
User message
     |
     v
Pi agent loop (model = session.llm_provider/llm_model)
     |
     +-- decides: plain factual/advice question
     |        -> calls search_transcripts(query)
     |
     +-- decides: user wants Ship30for30-style content
     |        -> calls generate_ship30_essay(topic, source_context)
     |
     +-- decides: user wants a document/UI snippet
              -> calls create_artifact(type, title, content)
```

### `search_transcripts` — hybrid retrieval

1. **Router step**: match query keywords against the 50 pre-built topic
   tags to produce a candidate episode set (cheap, no embedding call).
2. **Vector step**: pgvector cosine similarity search on
   `chunks WHERE episode_id = ANY(candidates)`, top-K.
3. **Fallback**: if the candidate set is empty or top scores fall below a
   relevance threshold, re-run the vector search across the full corpus.
4. Returns chunks + episode/guest metadata, used both to ground the
   answer and to populate citations.

### `generate_ship30_essay`

Loads a dedicated system prompt encoding the Ship30for30 structure (hook,
skimmable bolded/bulleted body, ~1250 words, clear takeaway) and generates
against the conversation's existing grounded context — it does not
re-retrieve from scratch, it reformats what's already been established.

### `create_artifact`

Persists `{type, title, content}` to the `artifacts` table linked to the
current message, and emits the `artifact_created` SSE event that the
frontend uses to open the viewer panel.

## 5. LLM toggle implementation

Each session stores `llm_provider` and `llm_model`. On every message, the
backend passes these to the Pi RPC call as the active model selection.

- **Cloud**: OpenAI (`gpt-4o-mini` or similar) is the confirmed cloud
  provider for this submission, picked up automatically from
  `OPENAI_API_KEY`. Anthropic support is left wired in via the same
  mechanism (`ANTHROPIC_API_KEY`) since Pi is provider-agnostic by
  design, but is not required for this submission.
- **Local (Ollama)**: registered via a generated `models.json` pointing
  at Ollama's OpenAI-compatible endpoint:

```json
{
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "compat": { "supportsDeveloperRole": false, "supportsReasoningEffort": false },
      "models": [{ "id": "llama3.1:8b" }]
    }
  }
}
```

The frontend exposes a simple dropdown in the session header
(`GPT-4o-mini (cloud)` / `Llama 3.1 (local)`); selecting an option calls
`PATCH /sessions/{id}/config`, persisted immediately.

### Error handling

- Missing cloud API key for the selected provider → fail fast with a
  structured error at the point of use, surfaced as a toast, not a
  generic 500.
- Ollama unreachable → caught at the RPC boundary, surfaced as
  "Local model unavailable — is `ollama serve` running?"
- Empty/low-confidence retrieval → the agent is instructed to say so
  explicitly rather than answering from general knowledge, preserving
  the "strictly grounded" requirement.

## 6. Known engineering tradeoff: Pi RPC vs. direct SDK calls

Pi's SDK is Node/TypeScript; the backend is Python — this requires an RPC
subprocess boundary rather than an in-process function call, which adds
minor latency per turn (subprocess round-trip vs. direct call). This was
accepted because it gets multi-provider model switching (cloud + local)
largely for free via Pi's own provider/model config, rather than
hand-rolling that abstraction in Python. If the RPC integration proved
unreliable under time constraints, the documented fallback is a direct
Anthropic/OpenAI SDK client in Python with an equivalent manual tool
router — same tool contracts, no subprocess dependency.
